## Data ownership and API contract

One atomic snapshot per confirmed, nonanonymous Auth user contains the entire existing validated planner v1: trips, itinerary (activities/accommodation/transport), packing, expenses/budgets and useful links. This avoids partial saves between itinerary and linked costs and allows a single account-wide compare-and-swap transaction. All of those entities inherit the snapshot's owner; separate trips can never be assigned to another account by a client-supplied field.

- `planner_private.documents`: `owner_id` UUID primary key references `auth.users`, monotonically increasing `revision` bigint, `planner` JSONB, `files` JSONB, `updated_at` timestamptz.
- `planner_private.tombstones`: `(owner_id,entity_id)` primary key, deletion revision/time. Retained indefinitely, including deleted trip child/file IDs; no client deletion privileges. A reviewed maintenance limit of100,000 tombstones/account fails closed, rather than purging history automatically.
- `planner_private.file_objects`: `(owner_id,object_id)` key, reserved immutable bytes/MIME and creation timestamp. Includes uploaded, staged and orphaned files in the100-object/20MiB limit. Reservations never expire/free quota automatically while bytes might remain.

RLS is explicitly enabled and forced on all three tables. Authenticated users receive owner-filtered SELECT, no direct table writes; anonymous users receive no table/schema access. The tables/helpers remain in **unexposed** `planner_private`; only RPCs live in the proposed exposed `planner_api`. Writers derive owner identity solely from verified `auth.uid()` plus `auth.users.email_confirmed_at` and nonanonymous status, not an owner argument. SECURITY DEFINER writers have empty search paths and explicit ownership checks. The SQL administrator/service-role remains privileged; ordinary RLS is **not end-to-end encryption** and does not conceal data from the Supabase administrator/provider. [Supabase API security](https://supabase.com/docs/guides/api/securing-your-api), [function security](https://supabase.com/docs/guides/database/functions).

Calls below are a **future client contract**, not executable integration in today's app. Use `client.schema('planner_api').rpc(name,arguments)` with the user's validated Auth session. Supabase's publishable key identifies a public app; user JWTs determine owner access. Secret/service keys bypass RLS and must never be in the browser. [API keys](https://supabase.com/docs/guides/getting-started/api-keys).

| RPC | Arguments | Result / behavior |
| --- | --- | --- |
| `read_document` | none | `{revision:"0",planner:{version:1,trips:[]},files:[],updatedAt:null,deletedIds:[]}` if a confirmed user has no row; otherwise own snapshot plus deletion IDs. Unconfirmed/anonymous access denies. |
| `commit_document` | `p_expected_revision` decimal bigint/string; `p_planner` existing v1 object; `p_files` manifest array | `{revision:"N"}` on atomic save. Initial expected revision0; subsequent saves require the latest acknowledged revision. Revisions returned as strings to avoid JS integer loss. |
| `reserve_file_object` | `p_object_id` fresh UUID, `p_bytes` integer1…5,242,880, `p_mime_type` allowlisted MIME | `userUUID/objectUUID` reserved object key. Same ID+size/type retry is idempotent; changing reservation rejects. Max100 reservations/20MiB, including pending/orphans. No owner/path parameter. |
| `list_file_objects` | none | Own `{objectId,size,type,createdAt}` records for pending upload/recovery/cleanup; no other owner records. |
| `release_file_object` | `p_object_id` UUID | `true` idempotently; refuses while own current manifest or Storage metadata still references the object. |

Commit errors: SQLSTATE`42501` account/access denied, `40001` stale revision conflict, `22023` invalid model/IDs/attachment/missing upload/tombstoned ID, `54000` quota/history limit. Future UI must check actual returned error codes and not assume successful HTTP responses mean bytes/state are durable.

## Private file lifecycle and recovery

Bucket`planner-attachments` is private with5MiB/type restrictions. Ownership gates require a confirmed user's exact UUID prefix and a second UUID path component. Restrictive policies prevent other permissive policies from authorizing cross-owner access, unreserved uploads, overwrites/moves or deleting currently referenced files. Narrow restrictive bucket metadata policies prevent anonymous/authenticated users from making the bucket public, weakening its limits, renaming or deleting it. Other buckets retain their existing policies. Public URLs and anonymous downloads must fail in live tests. [Storage access control](https://supabase.com/docs/guides/storage/security/access-control).

1. Keep original local text/files and a complete backup. Validate bytes/name/size/MIME, compute SHA256, generate objectUUID and reserve it via RPC. Reservation includes staged files in quota before upload.
2. Upload via the **Storage byte API**, exact returned path, `upsert:false`, with the user's session. Never INSERT/DELETE Storage database metadata manually in production. Server policy requires the reservation size/MIME to match actual incoming Storage metadata; this behavior must be confirmed against the real API before approval to enable sync.
3. Verify upload success and authenticated download/hash. Publish the manifest atomically with the planner at the expected revision. The RPC requires uploaded metadata and its reservation to exist. Mark Synced only after the acknowledged revision and all referenced byte downloads verify. A pending/missing upload is visibly pending, not a successful sync.
4. CAS conflict keeps local edits/original bytes. Refetch the server document and resolve as below. Retain staged objects still needed by local pending edits; clean only objects definitively abandoned by that pending operation. Never delete all files on network/auth failure.
5. Delete a file by removing its manifest ID in a successful document commit, which records its logical ID tombstone. Then call authenticated Storage remove for its now-unreferenced object. Deletion policy takes the same owner advisory lock as document commits and checks a fresh snapshot, so a live reference cannot be removed outside CAS. After Storage metadata is gone, release its reservation via RPC. Client cleanup failures retry later and remain charged to quota.
6. On startup/reconnect compare local pending entries, manifest and own reservation listing. Retry valid unfinished uploads; list abandoned unused reservations for explicit cleanup/recovery. Never auto-clear a pending offline operation's file. If a referenced object is absent/corrupt due to privileged operator action/provider loss, preserve metadata and healthy local originals; show a recovery state. Repair by validating local bytes, uploading to a fresh objectUUID and CAS-replacing that file's object reference; keep the logical ID. If no original exists, report unavailable and allow private backup recovery—do not invent contents or silently delete the itinerary.

Storage bytes and database snapshots are separate services; there is no atomic distributed transaction. Upload-before-publish, immutable versions, locks and verification minimize gaps but do not guarantee provider-level durability. The reservation gate's Storage metadata behavior, quota cleanup, file download errors and races require actual provider tests. Signed URLs are bearer access; do not create/store/share them in normal sync. Use authenticated downloads into local blobs for canvas previews and revoke temporary objectURLs. No attachment/API/Auth response is cached by the public-shell service worker or committed in source.

## Concurrent devices, offline edits and deletions

Store a durable last-acknowledged base snapshot/revision, current local edits and explicit operation journal under the signed-in user's namespace in IndexedDB. Keep local edits while offline or Auth expires. Outgoing changes must never set an owner ID. Do not mix a second account with existing local plans or change the owner of a journal when accounts switch; sign-in/first join offers private backup and explicit merge/copy choices.

Each upload attempts CAS with the acknowledged revision. Transactions serialize per owner; two devices committing the same revision cannot both win. On `40001`, preserve both local pending and fetched server copies. Rebase with a three-way comparison `(base,local,server)` by stable entity ID and field: apply nonconflicting additions/field changes, merge independent IDs, and present explicit choices for competing changes to the same field/attachment. Display original currency/timezone values. If deleting an entity competes with another device editing it, show that conflict; tombstones prevent sending the old deleted ID again. A user choosing restoration makes a new ID and remaps all references. Whole-trip deletion includes children/files and never silently reappears.

No timestamp last-writer-wins overwrite, no automatic whole-document replace from stale local data, no30-day tombstone expiry and no unbounded blind retry. Persist unresolved conflicts across reload. Recheck revision before any retry and retain all file originals until the chosen resolution commits. Server timestamps are informational; revisions determine ordering.

Account reset is a confirmed CAS commit of the blank planner/files, advancing the existing row and tombstoning all prior entities; it never deletes/recreates the document row at revision0. Clean unreferenced blobs afterward. Sign out/unlink clears only that device's Auth/session/cursor when requested; it does not delete local saved plans or cloud content. Full account deletion, provider retention and backup erasure need a separate reviewed process; user-FK cascade alone cannot delete Storage byte contents and does not constitute an implemented privacy erasure feature.

Initial sync uses the **same individual confirmed account** on phone and computer. Different accounts do not share trips. A future sync-code option must be separately designed as authenticated, short-lived, strong one-time device/workspace pairing with server-side hashes/expiry/rate limits and reviewed membership policies. It cannot be a public fixed password or a six-digit permanent shared bearer login. No pairing endpoint exists in this proposal.
